# 호텔 정보 추출 설계 레포트

> 목적별 호텔 추천 + 가격 모니터링·알람 시스템을 위한 데이터 추출 스펙

---

## 1. 개요 및 목표

본 시스템은 호텔 사이트에서 정보를 추출하여 두 가지를 수행한다.

1. **목적별 추천** — 사용자의 여행 목적(가족·출장·커플 등)에 맞는 호텔을 매칭·정렬한다.
2. **가격 모니터링·알람** — 사용자가 선택한 호텔의 가격·프로모션을 주기적으로 추적하여, 가장 좋은 가격이 제시되면 알람을 보낸다.

이 두 목적은 데이터의 성격이 다르다. 추천용 정보는 **상대적으로 잘 변하지 않고**, 가격 정보는 **자주 변한다**. 따라서 처음부터 두 종류의 데이터를 분리해 설계한다.

---

## 2. 핵심 설계 원칙

설계 전반을 관통하는 네 가지 원칙이다. 이후의 추출 스펙은 모두 이 원칙 위에 있다.

### 2.1 정적 프로필 vs 동적 가격 분리

호텔의 속성(위치·시설·리뷰 등)은 한 번 긁고 가끔 갱신하면 된다. 반면 가격은 시간에 따라 계속 변하는 시계열이다. 이 둘을 같은 테이블에 섞으면 관리가 어려워지므로, **프로필 테이블**과 **가격 이력 테이블**을 분리하고 호텔 고유 ID로 연결한다.

### 2.2 필터 vs 가중치 구분

사용자가 보는 조건은 성격이 두 가지다.

- **필터(deal-breaker)**: 없으면 후보에서 탈락하는 조건. 예) 반려동물 동반, 휠체어 접근성
- **가중치(preference)**: 없으면 감점이지만 다른 장점으로 상쇄 가능한 요인. 예) 평점, 시설 다양성, 가격
- **등급형(조건부) 필터**: 통과/탈락의 이진이 아니라, 충족 정도를 등급으로 나누는 조건. 침대 구성이 대표적이다.

중요한 점은 **같은 항목이라도 사용자마다 필터일 수도, 가중치일 수도 있다**는 것이다. 누군가에겐 수영장이 필수, 다른 사람에겐 "있으면 좋은" 항목이다. 따라서 각 항목의 필터/가중치 여부는 고정값이 아니라 사용자별 설정으로 둔다.

#### 등급형 필터가 필요한 이유 (침대 구성 사례)

"더블베드 2개"를 문자열로 정확히 매칭하면, **더블1 + 싱글1 + 엑스트라베드**로 충분히 가능한 방을 부당하게 탈락시킨다. 필터는 "스펙"이 아니라 **충족해야 할 니즈**에 걸어야 한다.

까다로운 점은 같은 요청이 사람마다 다른 니즈를 가리킨다는 것이다.

- **단순 수용 인원** ("4명이 잘 수 있으면 됨") → 엑스트라베드·소파베드·커넥팅룸 모두 대안이 됨
- **침대 타입 자체가 조건** (예: 두 커플이 각자 더블 사용) → 엑스트라베드로 대체 불가

따라서 시스템이 임의로 치환하지 말고, **충족 정도를 3단계로 표현**한다.

1. **완전 충족** — 요청한 구성 그대로 있음
2. **조건부 충족** — 엑스트라베드/소파베드 추가 시 가능 (추가 요금·정원 제한 표시 후 사용자 판단에 위임)
3. **불가** — 어떤 방법으로도 안 됨

> 조건부 충족 시 발생하는 **엑스트라베드 요금은 총액에 포함**해 비교해야 한다(섹션 G의 총액 정규화와 동일 원칙). 그렇지 않으면 조건부 방이 실제보다 싸 보이는 착시가 생긴다.

### 2.3 부대시설은 구조화된 객체로

시설을 `있다/없다`의 단순 boolean으로 긁으면 추천 품질이 떨어진다. 같은 "수영장"이라도 워터슬라이드 딸린 키즈풀이면 가족 신호, 성인 전용 인피니티풀이면 커플 신호로 정반대다. 따라서 시설은 **존재 여부 + 세부 속성 + 페르소나 신호**의 3겹 구조로 추출한다.

### 2.4 결정은 깔때기 구조

사람이 호텔을 고르는 과정은 깔때기 모양이며, 시스템의 처리 흐름도 이와 동일하다.

1. **필터로 후보 거르기** — 필수 조건 미충족 호텔 제외
2. **가중치로 정렬** — 평점·시설·위치·가격으로 점수화
3. **사진·리뷰로 최종 확정** — 사용자가 마지막에 보는 단계
4. **선택된 소수(shortlist)에만 가격 모니터링** — 전체 추적은 비용이 폭발하므로, 1~3을 통과한 호텔에만 주기적 크롤링·알람을 건다

## 3. 추출 필드 스펙

각 항목에 다음을 표시한다.

- `[필터]` — 없으면 탈락하는 조건으로 쓰일 수 있는 값
- `[가중치]` — 정렬·점수화에 쓰이는 값
- 가격 관련(섹션 G)은 별도 동적 테이블로 관리

### A. 식별·기본 정보 (두 테이블 공통 키)

| 항목 | 설명 |
|------|------|
| 고유 ID | 사이트별 hotel_id, 가능하면 OTA 간 매칭용 키 |
| 호텔명 | |
| 브랜드/체인 | |
| 공식 성급(star) | |
| 사이트 URL | 재크롤링용 — **필수** |

> 가격 모니터링은 "같은 호텔·같은 방·같은 조건"을 시간에 따라 추적하므로 **고유 식별자가 흔들리면 전체가 무너진다.**

### B. 위치·교통 정보

핵심 원칙: 거리·소요시간을 사이트 표기에 의존하지 말고, **좌표를 정확히 추출한 뒤 지도 API로 직접 계산**한다. 사이트마다 "도심까지 X km" 기준이 제각각이라 그대로 쓰면 비교가 불가능하다.

| 항목 | 태그 | 설명 |
|------|------|------|
| 위도/경도 | — | 모든 거리 계산의 출발점 |
| 주소·동네/지역명 | [가중치] | 도심/해변/주거지 등 동네 특성 |
| 가장 가까운 역 + 도보 거리 | [필터/가중치] | 대중교통 접근성 |
| 공항·기차역·터미널까지 거리·소요시간 | [가중치] | |
| 주요 관광지/랜드마크까지 거리 | [가중치] | 목적지 기준 |
| 비즈니스 지구 근접성 | [가중치] | 출장 |
| 해변·스키장 등 목적 근접성 | [가중치] | |
| 공항 셔틀 유무 | [필터] | |
| 주차 | [필터] | 자차 여행객 |
| 주변 편의(편의점·마트·식당가)·치안 | [가중치] | 혼행·가족에 중요 |

### C. 객실 정보 (필터의 핵심 영역)

| 항목 | 태그 | 설명 |
|------|------|------|
| 룸 타입 | [필터/가중치] | |
| 기본 침대 구성·수 | [등급형 필터] | 타입·개수. 단순 매칭이 아닌 충족 등급 판정 (2.2 참조) |
| 엑스트라베드/소파베드 | [등급형 필터] | 추가 가능 여부 + 요금 + 정원 제한 |
| 표준 정원 / 최대 정원 | [필터] | 엑스트라베드 포함 시 최대 정원 구분 |
| 가족룸/커넥팅룸 | [필터] | 가족여행. 침대 니즈의 대안 충족 경로 |
| 객실 면적 | [가중치] | |
| 취사 시설(키친) | [필터] | 워케이션·장기 숙박 |
| 객실 내 책상·와이파이 속도 | [가중치] | 출장·워케이션 |

침대·수용 정보는 단순 문자열이 아니라 **확장성까지 담은 객체**로 저장한다. 그래야 매칭 로직이 "이 일행을 *허용 가능한 방식으로* 재울 수 있는가?"를 계산할 수 있다.

```json
{
  "beds": [
    { "type": "double", "count": 1 },
    { "type": "single", "count": 1 }
  ],
  "standard_occupancy": 3,
  "max_occupancy": 4,
  "extra_bed": { "available": true, "fee": 30000, "max": 1 },
  "sofa_bed": false,
  "connecting_room": true
}
```

> 매칭 결과는 **완전 충족 / 조건부 충족(엑스트라베드 추가 요금 표시) / 불가** 3단계로 사용자에게 제시한다. 조건부 충족의 엑스트라베드 요금은 가격 비교 시 총액에 합산한다(섹션 G).

### D. 부대시설 (구조화된 객체)

| 분류 | 추출할 속성 | 태그 |
|------|-------------|------|
| 물놀이 | 수영장 개수·실내외·크기·운영시간·계절·워터파크·키즈풀·성인전용 | [가중치, 일부 필터] |
| 키즈·가족 | 키즈클럽(연령)·놀이터·베이비시팅·유아용품 대여 | [가중치] |
| 웰니스 | 스파·사우나·온천 | [가중치] |
| 식음 | 조식 제공·형태·레스토랑 수·바·올인클루시브 | [필터/가중치] |
| 운동·액티비티 | 헬스장·코트·골프·워터스포츠·자전거 | [가중치] |
| 비즈니스 | 회의실(수용)·코워킹·고속 와이파이 | [가중치] |
| 편의·접근성 | 24h 프런트·세탁·반려동물·휠체어 접근성·엘리베이터 | [필터] |

부대시설 저장 구조 예시 (컬럼으로 펼치지 말고 객체로):

```json
{
  "facility": "swimming_pool",
  "exists": true,
  "attributes": {
    "count": 3,
    "has_water_park": true,
    "has_kids_pool": true,
    "adults_only": false,
    "indoor_outdoor": "both",
    "seasonal": false
  },
  "persona_signals": ["family", "kids"]
}
```

이렇게 하면 추천 단계에서 `attributes.has_water_park = true` 같은 단순 필터링이 가능하고, 새 속성이 생겨도 스키마를 깨지 않고 추가된다.

### E. 리뷰·평판 `[가중치]`

| 항목 | 설명 |
|------|------|
| 종합 평점 + 리뷰 수 | |
| 세부 점수 | 청결도·위치·서비스·가성비 |
| 리뷰 키워드/감성 | 페르소나 매칭용 ("조용함", "조식 훌륭" 등) |
| 대표 사진 | 추천 UI·최종 확정 단계 |

> 청결도는 거의 모든 예약 행동 연구에서 최상위 결정 요인이므로 세부 점수로 반드시 확보한다.

### F. 정책

| 항목 | 태그 | 설명 |
|------|------|------|
| 체크인/아웃 시간 | [가중치] | 늦은 체크인 등 |
| 취소 정책(환불 가능 여부) | [필터/가중치] | **가격 전략에 직결** |
| 흡연 여부 등 | [필터] | |

### G. 가격·프로모션 (동적 — 별도 시계열 테이블)

가격은 단독으로 의미가 없다. **항상 "조회 조건"과 묶어야** 비교가 가능하다. 이 섹션만 자주 크롤링한다.

| 항목 | 설명 |
|------|------|
| 가격 + 조회 조건 | 룸타입·투숙 인원·체크인/아웃 날짜·통화 |
| 세금·수수료 포함 총액 | 표시가 vs 총액 — **정규화 필수**. 조건부 충족 시 엑스트라베드 요금도 합산 |
| 프로모션·할인 | 할인율·멤버가·부가혜택(조식포함 등) |
| 잔여 객실·예약 가능 여부 | |
| 수집 시각(timestamp) | 시계열·역대 최저가 판단의 기준 |
| 출처(OTA) | |

## 4. 페르소나별 핵심 결정 요인

여행 목적별로 우선순위가 다르다. 추천 매칭의 기준이 된다.

| 페르소나 | 핵심 요인 (대표 3가지) |
|----------|------------------------|
| 출장 | 위치(미팅·역 근처) / 빠른 와이파이·책상 / 늦은 체크인·조용함 |
| 가족여행 | 가족룸·침대 구성 / 키즈·물놀이 시설 / 조식(아이 무료 여부) |
| 커플 | 분위기·객실 디자인 / 뷰·성인전용·조용함 / 스파·근처 식당 |
| 혼행·배낭여행 | 가격 / 대중교통 접근성 / 리뷰·안전 |
| 럭셔리·휴양 | 브랜드·서비스 수준 / 시설 완성도 / 올인클루시브·스파 |
| 워케이션 | 와이파이 속도 / 장기 요금·세탁·취사 / 조용한 업무 공간 |

거의 모든 페르소나가 공통으로 보는 요인: **가격/가성비, 위치, 평점·리뷰, 청결도, 취소 정책.**

## 5. 페르소나 점수화 방법

각 시설·속성이 페르소나별 점수에 가중치로 기여하도록 설계하면 추천 정렬이 깔끔해진다.

예시 가중치:

- 워터파크 → 가족 +3
- 키즈클럽 → 가족 +2
- 성인 전용 풀 → 커플 +3
- 고속 와이파이·업무 책상 → 출장/워케이션 +2

호텔마다 "가족 87점 / 커플 40점"처럼 산출하여 사용자 페르소나에 맞게 정렬한다.

추가로, 사용자가 **명시적으로 입력한 선호**와 **실제로 클릭·저장한 호텔의 공통 속성**을 함께 반영해 가중치를 보정하면 정확도가 올라간다. 사람들은 자기 우선순위를 말로는 잘 정리하지 못해도 행동으로는 드러내기 때문이다.

## 6. 시스템 아키텍처·데이터 흐름

```
[1] 호텔 리스트 확보
        │
        ▼
[2] 사이트 방문 → 프로필 정보 추출 (섹션 A~F)
        │         (1회 추출 + 주기적 갱신)
        ▼
[3] 사용자 조건 적용
     ├─ 필터로 후보 거르기
     ├─ 가중치·페르소나 점수로 정렬
     └─ 사진·리뷰로 최종 확정
        │
        ▼
[4] shortlist 선정
        │
        ▼
[5] shortlist에만 가격·프로모션 주기 크롤링 (섹션 G)
        │         → 가격 이력 테이블에 시계열 적재
        ▼
[6] 역대 최저가·프로모션 감지 → 사용자 알람
```

테이블 구성:

- **호텔 프로필 테이블** — 섹션 A~F. 한 번 적재, 가끔 갱신.
- **가격 이력 테이블** — 섹션 G. hotel_id로 연결, 시계열 적재.

알람 로직은 결국 "이 호텔의 이 조건에서, 지난 N일 중 현재가 최저인가?"라는 단순 쿼리로 풀린다.

## 7. 구현 시 주의사항

- **고유 ID 안정성**: 가격 추적의 근간. OTA 간 동일 호텔 매칭 키도 확보할 것.
- **좌표 우선 추출**: 거리·소요시간은 좌표로 직접 계산. 사이트 표기 의존 금지.
- **가격 정규화**: 세금·수수료 포함 여부가 사이트마다 달라 그대로 비교하면 "최저가"가 거짓이 된다. 반드시 총액 기준으로 통일. 조건부 충족 객실은 엑스트라베드 요금까지 포함해 비교.
- **침대 조건은 등급형으로**: "더블 2개" 같은 조건을 문자열 매칭하지 말 것. 충족해야 할 니즈(수용 인원 또는 침대 타입)에 걸고, 완전/조건부/불가 3단계로 판정한다.
- **타임스탬프 필수**: 모든 가격 수집에 시각을 남겨야 시계열 분석·역대 최저가 판단이 가능.
- **"가장 좋은 가격"의 정의**: 단순 최저가가 아니라 **환불 가능 여부·총액 기준**으로 잡는다. 비환불 최저가에 묶였다가 더 싼 환불 가능 옵션을 놓치는 경우가 흔하다.
- **모니터링 범위 제한**: 전체 호텔이 아닌 shortlist에만 가격 크롤링을 걸어 비용을 통제.
- **필터/가중치 태그는 사용자별 가변**: 같은 항목이 사람마다 필수일 수도, 선호일 수도 있다.
